When ShopFast breaks at two in the morning, an engineer spends the first forty minutes not repairing anything — just working out what happened, across six tools. AIRP does that reconstruction in about ninety seconds, cites its sources, and then stops and asks permission before it touches anything.

What happened next

Six agents, each with one narrow job

  1. Monitoring

    Confirms the alert is a real signal rather than noise, and sets its severity.

  2. Correlation

    Resolves the alert to a service, a namespace, a pod and a source repository.

  3. Root cause

    Plans what evidence it needs, then collects it — pod state, events and rollout history from Kubernetes, commits and pull requests from GitHub, image metadata from the registry. Read-only throughout.

  4. Remediation

    Drafts a minimal, reversible fix. Drafts it. Nothing executes without a human decision.

  5. Documentation

    Writes the incident record while the context is still fresh — the step teams skip.

  6. Memory

    Embeds the incident so the next one that looks like it arrives with precedent attached.

The whole sequence runs as a durable workflow. If a node dies mid-investigation, it resumes exactly where it stopped — nothing is lost and nothing runs twice.

The output

Three ranked hypotheses, not one guess

Produced by a live model call against live infrastructure. No service names, image tags or job names were configured in advance — the platform found them.

Leading hypothesis 0.72

The checkout container exceeded its Kubernetes memory limit and was OOMKilled — either a leak or an undersized limit. The auto-update-deployments job may have rolled out an image with higher memory consumption.

Alternative 0.65

The s1-checkout image has no manifest entry matching the node architecture — an arm64 / amd64 mismatch introduced by the same automated deployment job.

Contributing factor 0.40

The deployment job cycles multiple workloads every thirty minutes. The resulting churn raises memory pressure on the node.

The part that matters

Built to be doubted

An assistant that is confidently wrong during an incident is worse than no assistant. Every design decision below exists to make that failure mode visible rather than quiet.

Claims carry citations

A hypothesis referencing evidence the platform did not actually collect is rejected automatically, before anyone reads it.

Low confidence escalates

Below the configured threshold it hands over to a human rather than asserting more loudly.

Investigation cannot write

Evidence collection holds read-only credentials. Changing anything is a separate, gated path.

Approval before action

Remediation plans, pull requests and issues wait for an explicit human decision.

Secrets never reach the model

Payloads are redacted before any prompt leaves the platform.

Every call is auditable

Model name, prompt version, latency and a hash of each response are recorded and replayable months later.

Running it for real

Local today, managed services tomorrow

The demo environment runs on a local Kubernetes cluster so it can be shown anywhere, including on a plane. Every component has a managed IBM Cloud equivalent, and the swap is configuration rather than a rewrite.

Alert bus — Kafka locally, IBM Event Streams in production.

State and memory — Postgres with vector search and Redis, both available as managed services.

Workloads — any conformant Kubernetes, including IBM Kubernetes Service.

Inference — IBM models throughout. Your source code and incident data stay inside your tenancy.

Alerts arrive from whatever you already run — Prometheus, Instana, Dynatrace. AIRP replaces none of it. It consumes what those tools emit and does the work that currently lands on a person.
